# CSO Security Sign-Off — Issue #14 (Bounded Automated Repair)

**Date:** 2026-09-01
**Scope:** Diff since `a40a145`: `migrations/0026_v2_automated_repair.sql`, `src/domain/automated-repair.ts`, `tests/v2-automated-repair.test.ts`, vitest include entry.
**Reviewer:** AI-assisted CSO pass (morabeza-cso skill). Not a substitute for an external audit.

## 1. What was audited
Fix Coordinator / Release Blocker Fix AI stages, repair-batch application, confirmation QA, terminal resolution (`RELEASE_READY` / `BLUEPRINT_REVIEW_REQUIRED` / `HUMAN_REVIEW_REQUIRED`), Degraded/Failed classification, and the storage ledger.

## 2. Security scope
Internal domain services only — no new public routes, no secrets, no payment flows, no destructive operations. Trust boundaries: model-output → plan validation → application-service mutation (PRD §24 pattern), and workflow-state writes.

## 3. Attack-surface summary
- Model-driven plan content (fix-coordinator / release-blocker-fix outputs).
- D1 writes: `repair_batches`, `build_versions` (via `createNextBuildVersion`), `build_workflow_events`, release records via #13 gate.
- AI stage runs with provenance (`ai_stage_runs`).

## 4. Findings

### Verified properties (no finding)
- **Mutation boundary:** the versioned `FixPlanSchema` (`additionalProperties: false`, `target ∈ {implementation, image}`, strategy enum) makes fact/reference/build-mode/blueprint mutations unrepresentable; `applyRepairBatch` performs no content changes itself. The text lint is secondary hardening only.
- **Budget ceiling:** `UNIQUE (build_id, kind)` enforces one Fix Coordinator batch + one Release Blocker Fix per Build at the storage boundary; immutability triggers protect the ledger. No unbounded retry loop is reachable.
- **Isolation/audit:** every query is bound by build/version ids; every transition appends an immutable workflow event.

### W1 — Orphan version under concurrent batch application (Watch item, Low)
Two concurrent `applyRepairBatch` calls could each create a new Build Version before one INSERT loses the uniqueness race, leaving an unused immutable version. Harmless (unused candidates are inert), and the single-threaded Workflow step semantics make this unreachable in the intended orchestration. Monitor only.

### W2 — Caller-supplied confirmation reports (Watch item, Low)
`resolveAfterConfirmation` forwards caller-provided QaA/QaB reports to `assignReleaseReady`; version pinning is enforced against the input ids, not against where the reports were produced. In the intended orchestration the same context object flows through, and the `qa_report` artifact is persisted per version — but a future orchestration bug could pair v3's context with v2's reports. Suggested hardening for a later pass: load confirmation reports from `ai_stage_runs`/artifacts by version id inside the release gate instead of accepting them by value.

### W3 — Model-derived text in event details (Watch item, Low)
`blueprintReviewReason` (≤2000 chars, schema-bounded) flows into `build_workflow_events.detail`. No HTML rendering exists today; escape model-derived detail text if an operator UI ever renders it inline.
