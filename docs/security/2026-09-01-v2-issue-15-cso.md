# CSO Security Sign-Off — Issue #15 (Approval, Publication, Rollback)

**Date:** 2026-09-01
**Scope:** Diff since `b78ed69`: `migrations/0027_v2_publication.sql`, `src/domain/publication.ts`, `tests/v2-publication.test.ts`, `env.d.ts` (`ROLLBACK_WINDOW_DAYS`).
**Reviewer:** AI-assisted CSO pass (morabeza-cso skill). Not a substitute for an external audit.

## 1. What was audited
Approval of an exact Release Ready Build Version, separate Publication of that exact version (including operational failure retry), Rollback Version retention/restore, and the publication state machine.

## 2. Security scope
High-sensitivity by classification (release authority + deployment state), but **no new public routes**: all entry points are internal domain services behind the operator HMAC/workflow boundary. No secrets, no payment flows, no visitor input.

## 3. Attack-surface summary
- D1: `build_approvals` (immutable, unique per version), `publications` (append-only attempt ledger), `site_published_state` (single row per Site).
- Deployment: production publish path reuses the audited assets-only deployer (no script, no secret bindings, sanitized worker names).
- Immutable R2 candidate reads keyed by build/version.

## 4. Findings

### Verified properties (no finding)
- **Approval drift prevention:** approval requires an existing Release Ready record for THAT version; the row is unique per version with immutability triggers and is pinned to the artifact manifest hash; a changed hash yields `APPROVAL_HASH_MISMATCH`. A different version structurally cannot inherit an approval (lookup is by version id).
- **Approval ≠ live:** approval writes only its row + an `APPROVED` event — no deployment, no site-state change (test-verified).
- **Exact-version publication:** candidate bytes are loaded from immutable storage per the assembled manifest; any missing file aborts the publish **before** deployment (no partial/other-content publish). Idempotence short-circuits only when the version is the *current* Published Version.
- **Rollback safety:** restores the retained prior version with zero new Build/Version/Approval rows, preserves all publication history (no deletes anywhere), leaves Site Configuration untouched, enforces the retention window.

### W4 — Operator routes for Approval/Rollback are not exposed yet (Watch item, Medium — gates production exposure, not this scope)
`approveBuildVersion`/`rollbackPublication` are internal services. There is currently no unauthenticated surface, so no exploit path exists in this diff. Before any production operator UI/route exposes them, they MUST be gated by short-lived capability tokens binding `buildId + buildVersionId + artifactManifestHash + action + expiry` (the V1 `signApprovalToken` pattern is the precedent and the crypto helpers already exist). Recorded as a hard precondition for the exposure work.

### W5 — Concurrent publication race on the rollback pointer (Watch item, Low)
`site_published_state` is read-then-written during publish; two concurrent publications for one Site could mis-set the retained rollback version. The single-threaded Workflow orchestration makes this unreachable in the intended path; if publication ever becomes route-triggered, wrap the state swap in a D1 transaction/conditional update.

### W6 — Failure metadata hygiene (Watch item, Low)
`publications.error` stores exception text (sliced to 500 chars). Keep provider/transport error text out of any future public rendering.

## 5. Severity summary
Critical 0 · High 0 · Medium 1 (W4 — exposure-gating precondition) · Low 2 (W5, W6). No blocking findings for this issue's scope.

## 6. Required remediation
