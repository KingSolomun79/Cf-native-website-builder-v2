## 1. What was audited

The H2 wiring: the production email transport endpoint (the "Cloudflare-native
outbound email router") implemented as a dedicated Worker, the Form Service
transport channel to it (public URL fallback + same-account service binding),
the cron-driven bounded retry sweep, and the live staging-equivalent
verification path. No production (V1-live) worker or prod D1 was touched.

## 2. Security scope

High-sensitivity by classification: **new public endpoint** (`POST /send`),
**new shared secret** (`WAZIBIZ_EMAIL_TRANSPORT_TOKEN`, Worker secret on two
Workers), **provider credential handling** (`SMTP2GO_API_KEY`, router-only),
and a **new background mutation surface** (scheduled delivery retry sweep).

## 3. Attack-surface summary

- `https://wazibiz-email-router.wazibizwebsites.workers.dev` — `POST /send`
  (bearer-authenticated, exact-key-set JSON contract), `GET /health`
  (liveness only, `{ok:true}`, no configuration state), 404/405 otherwise.
- Service binding `EMAIL_ROUTER` (account-internal channel; the router's
  bearer check still applies — the binding does not bypass authentication).
- Scheduled handler every 10 minutes: re-invokes the existing
  `processDueEmailDeliveries` (idempotent, `MAX_DELIVERY_ATTEMPTS = 5`).
- Smoke script (`scripts/form-service-smoke.mjs`): credential-free; speaks
  only to the public submit route and reads D1 via `wrangler d1 execute`.

## 4. Findings

### F1 — Cron sweep was not registered on the worker handler (Medium — caught live, fixed in-diff)
The first staging deploy exported `scheduled` as a named export beside
`export default app`; the runtime uses the default export as the handler
object and ignores named exports beside it, so the cron fired into
`"Handler does not export a scheduled() function"` (live tail evidence,
15:10 UTC invocation). The unit test had called the named export directly
and could not see the registration shape. **Fixed:** the default export is
now an explicit handler object (`{ fetch, scheduled }`), and a regression
test asserts both handlers exist on the default export.

### Verified properties (no finding)

- **Fail-closed at every configuration level, live-verified:** transport URL
  unset → `transient / "email transport not configured"` (staging probe 1);
  router provider key unset → `503` → `transient / "transport responded 503"`
  through the live router with valid bearer auth (staging probes 8-9); no
  bearer token secret on the router → `503` before any auth comparison.
  Acceptance (202 + durable submission) never depends on delivery — the
  ledger records the failure class, matching PRD 37.
- **Auth ordering and cost:** the router authenticates (digest-based
  constant-time bearer compare) *before* reading the request body;
  unauthenticated callers cannot spend parse budget. Missing router token
  secret answers 503 without an auth oracle.
- **401 classifies permanent (loud):** a wrong token is caller
  misconfiguration; the Form Service records `permanent_failure` immediately
  (`tests/v2-email-router.test.ts`, binding test with 401 → permanent). This
  makes token-rotation drift visible instead of silently retrying.
- **No credential exposure:** the SMTP2Go `api_key` exists only inside the
  router→ESP request body (fixed TLS endpoint, code constant — no SSRF
  surface; `WAZIBIZ_EMAIL_TRANSPORT_URL` is deploy-time operator config,
  never request-derived). Router responses are fixed strings plus a coarse
  upstream code — never upstream bodies or secrets. Tests assert neither the
  shared token nor the provider key appears in responses or the outbound
  request headers. `git diff` and a repo-wide grep confirm no token material
  in tracked files; `.dev.vars` (which holds the generated staging token) is
  gitignored.
- **Generated Sites see nothing:** browser code POSTs only to the public
  form route; the transport URL/token live exclusively in Worker
  vars/secrets (re-verified against the #11 payload allowlist and the
  assets-only static-deploy contract).
- **Input hardening in depth:** the router re-validates the exact key set
  (rejects `template`/`recipient`-style smuggle keys), string types, plain
  email shapes for `to`/`from`/`replyTo`, CRLF rejection (header-injection
  defense on top of the Form Service's own parse-time rejection), length
  caps, and a 64 KB body ceiling → 422 permanent.
- **Retry sweep safety:** `scheduled` only re-invokes the existing bounded,
  idempotent sweep (per-submission attempt ceiling, terminal-state
  short-circuit); no visitor input, no new write paths.
- **Staging exposure:** `cf-website-factory-staging` runs the full route
  table, but mutating routes are HMAC-gated and fail closed without
  `WEBHOOK_SECRET` (unsigned → false; missing secret throws → 500). Its D1
  is isolated from production; prod D1 and the V1-live production worker
  were never touched (live deployment states verified during the session).

### W-28a — Form Service transport call has no timeout (Low, watch)
The transport `fetch`/binding call itself has no `AbortSignal.timeout`. The
router aborts its downstream call at 15 s, bounding the realistic stall, but
a hung router before its own timeout could hold a submit request. Hardening:
add `AbortSignal.timeout` to the transport call in a future pass.

### W-28b — Router has no rate limiting of its own (Low, watch)
Unauthenticated requesters can solicit cheap 401s. The authenticated path is
reachable only by platform Workers holding the token, and legitimate-path
load is bounded by the Form Service's per-site/IP submission limits. Account
-level protections apply. Non-blocking.

### W-28c — Retry sweep has no batch cap (Low, watch)
A large backlog of due transient deliveries processes sequentially within
one cron invocation; CPU limits abort it and the next 10-minute slot
resumes. Self-limiting, but a batch ceiling is a reasonable future
hardening.

### W-28d — Production wiring is deploy-coupled (operational, tracked)
Cloudflare blocks secret changes on `cf-website-factory` while the latest
uploaded version is undeployed (live version is still V1, per the #27
audit). The production runbook must, at V2 deploy time: (1) set
`WAZIBIZ_EMAIL_TRANSPORT_TOKEN` on `cf-website-factory` — until then the
config-carried URL means a production submission would reach the router
unauthenticated and terminal-fail permanently (loud by design); (2) set
`SMTP2GO_API_KEY` on `wazibiz-email-router` (the only missing credential;
until then the router correctly fails closed 503 → bounded transient retry).
The token value currently lives only in the local gitignored `.dev.vars`
(rotation at deploy time is acceptable and documented).

### W-28e — Same-account `*.workers.dev` fetch limitation (platform gotcha)
Workers cannot fetch each other's `*.workers.dev` URLs within one account —
the edge unrouts the same-zone subrequest and answers 404 (live-verified:
staging probes 3-7 recorded `permanent_failure / "transport responded 404"`
with zero router invocations, while external curl reached the router
normally). All same-account Worker→Worker HTTP must use service bindings.
Candidate for `PROMOTE_QUEUE.md`.

### W-28f — Default sender identity is a placeholder (operational)
`noreply@mail.wazibiz.example` is not a real verified sender. Once the
provider key is set, ESP-side verification will reject it (422 permanent)
unless Site Configuration sets an actually-verified platform sender —
production onboarding must configure real Sender Identities, and the
verified domain must be arranged on the provider account.

## 5. Severity summary

No Critical or High findings. Watch items: W-28a/W-28b/W-28c (Low,
hardening), W-28d/W-28f (operational, deploy-coupled), W-28e (platform
gotcha, documented).

## 6. Required remediation

are the issue's own runbook) and are recorded in the verification evidence.

## 7. Watch items
